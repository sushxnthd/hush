hush·Scope & policies

Privacy needs a clear boundary.

Updated October 8, 2026Hush support ↗

Understand what each surface protects, what it cannot promise and what remains to be validated.

Protect the saved workspace.

  • AES-256-GCM encryption with authenticated headers and random nonces.
  • PBKDF2-SHA256 key derivation with 600,000 iterations and a random salt.
  • Only ciphertext and envelope metadata are persisted.
  • Passphrase-derived key is non-exportable; idle lock clears app state.
  • Approval-gated memory selection and explicit review before clipboard copy.
  • Content Security Policy disables network connections in the app.

The page can read plaintext while unlocked. Encryption at rest does not protect against a compromised host, browser, extension or malicious code served from the site. Copying or pasting intentionally discloses the selected text. The browser workspace is not the runtime’s bounded private-computation engine.

A deeper, defined control surface.

The local core implements encrypted private state, repeated explicit-disclosure accounting, native bounded MCP tools, scoped action approvals, secretless credential brokerage and signed receipts. Production mode requires same-device client authentication and supported OS-key handling.

Timing, network metadata, compromised hosts, covert channels, unsupported clients, semantic inference and workflows bypassing Hush remain outside the current guarantees.

Read the full threat model ↗

Built does not mean independently validated.

Hush is early access. Before broad production claims, the project needs production provider registrations, live-provider end-to-end validation, signed distribution, long-duration reliability evidence and independent security/privacy review. Automated tests and synthetic benchmarks are evidence within their scope, not certification.

Report responsibly.

Follow the repository security policy. Do not place credentials, private data or sensitive exploit details into public issues.
